# ADR-001: Persistencia en capas simples; Observer cubre el cambio conocido de notificación

## Estado

Aceptado — 2026-11-12.

## Contexto

El sistema tiene tres categorías, tres verificaciones y tres interesados. No existe un plan de
cambio de motor de base de datos ni evidencia de un horizonte de tres años con sustituciones
de persistencia. Contabilidad sí anuncia una API externa para el próximo trimestre.
Se evalúa el criterio de la sección 6.2 de la guía: Hexagonal se justifica ante vida prolongada
y cambios reales de infraestructura, no solamente porque un diagrama simétrico resulte atractivo.

## Alternativas

1. Hexagonal completa: puerto RepositorioSolicitudes y adaptador JPA, más un nuevo puerto genérico de notificación.
2. Capas simples en persistencia y mantener ObservadorCambioEstado como frontera existente.

## Decisión

Se adopta la alternativa 2. SolicitudReembolsoService depende directamente de
RepositorioSolicitudesJpa. Un puerto paralelo hoy duplicaría firmas sin un consumidor o proveedor
alternativo que lo requiera (YAGNI/KISS). El dominio no importa JPA: META-INF/orm.xml contiene el
mapeo externo, conservando el repositorio directo exigido sin agregar entidades espejo ni mappers.

No se cambia la notificación: ObservadorCambioEstado permite sustituir el interior de
NotificadorContabilidad por un cliente de la API futura sin modificar el servicio ni a empleado/auditoría.
Un segundo puerto genérico por encima de esa interfaz no resolvería una variabilidad adicional.
La entrega fiable, las transacciones distribuidas y reintentos no se afirman resueltos por Observer:
se definirán cuando exista el contrato real de la API y sus requisitos de disponibilidad.

## Consecuencias positivas

- Menos interfaces, duplicación de modelos y mappers sin uso real.
- La variabilidad funcional ya está separada mediante Chain, Strategy y Observer.
- El cambio de infraestructura con fecha conocida tiene un punto de extensión existente.

## Consecuencias negativas

- La aplicación queda acoplada a la API de Spring Data; una persistencia ajena a JPA requeriría refactorizarla.
- El mapeo XML debe mantenerse alineado con los atributos del dominio.
- Las notificaciones son síncronas y no tienen garantía de entrega frente a fallos externos.
- La asimetría exige documentar el criterio para evitar confundirla con una migración hexagonal incompleta.

## Reconsideración

Introducir el puerto de persistencia si aparece un segundo adaptador real, migración fuera de JPA
o un ciclo de vida con sustituciones planificadas. Para Contabilidad, evaluar cliente específico,
outbox/reintentos e idempotencia cuando el contrato y SLA de la API los exijan.
